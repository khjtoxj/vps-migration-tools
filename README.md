## 迁移前，先做四件事

迁移翻车，多数坏在准备阶段。动手之前把这四件事做完，后面基本不会出大问题。

1. **摸清数据量。** 用 `du -sh /var/www /home` 这类命令统计网站文件、数据库、日志的总大小。数据量决定搬法：几个 GB 和几百 GB 是两套完全不同的打法，也决定了传输时间的下限。
2. **选好时间窗口。** 安排在业务低峰，并按预估时长留出至少 1.5 倍余量。有人在业务高峰期给电商平台迁移，订单接口直接超时两小时，就是数据量没估准、窗口没选对的结果。
3. **准备回滚预案。** 源机做一份快照或全量备份，存到独立位置（对象存储、本地硬盘都行），别和源机、新机放在同一个机房。万一新机起不来，老机还在，业务就不算断。
4. **把 DNS 的 TTL 调低。** 服务绑了域名的话，提前把 TTL 改到 300 秒左右。等迁移完再改解析，TTL 3600 的记录会让一部分用户多看一个小时的旧 IP。很多教程不提这一步，但它直接决定切换后有多少用户被甩在老机器上。

## 三种搬法怎么选

方法没有高下之分，按数据量和场景选：

| 方法 | 适合场景 | 停机时间 | 上手难度 |
| --- | --- | --- | --- |
| tar 打包 + scp 传输 | 几 GB 内的一次性搬家 | 短 | 低 |
| rsync 增量同步 | 大数据量、要控制停机窗口 | 可压到分钟级 | 中 |
| 商家快照导入 | 同一商家两台机器之间 | 很低 | 低 |

tar + scp 是最原始的搬法，把关键目录打成一个压缩包传过去：

bash
tar -cvpzf backup.tgz --exclude=/proc --exclude=/sys --exclude=/dev --exclude=/run --exclude=/tmp --exclude=/lost+found /
scp backup.tgz root@新机IP:/root/


这里有个老教程很少提醒的坑：如果打算把 tar 包解开直接覆盖新机根目录，排除清单还得加上 `/boot`、`/etc/fstab` 和网络配置文件。老机的内核、磁盘挂载表、网卡名跟新机对不上，解压完一重启，新机大概率失联，只能进救援模式手动修。搬数据没问题，整盘复制要格外小心。

rsync 是多数情况的最优解，支持增量同步和断点续传，只传有变化的部分：

bash
rsync -avz --progress /source/path root@新机IP:/target/path


传输中途断了（比如报 `Connection reset`），先检查防火墙放没放行 22 端口，然后加 `--partial` 参数接着传。

快照方法则依赖商家。搬瓦工这类自带 KiwiVM 面板的商家支持把快照导出成 VEID 和 TOKEN，再导入自家另一台机器，同商家迁移基本是一键的事。但快照默认只保留 30 天、粘性快照最多设 2 个，目标机硬盘还不能小于源机——这套机制只在同商家内部通用，跨商家就帮不上忙了。

## 手把手迁移：以 rsync 为例

rsync 迁移的核心是双阶段同步：先把九成的活儿在业务不停机的情况下干完，真正停机的只剩最后几分钟。

### 第一步：新机初始化

给新机装上和源机相同大版本的系统（Ubuntu 22.04 搬 Ubuntu 22.04，别跨大版本），装齐 Nginx、PHP、MySQL 等运行环境，配置 SSH 密钥免密登录，确认防火墙放行 22 端口。两机跨机房的话，先用 `ping` 测一下延迟，最好低于 100ms；延迟高、丢包多，传输速度会很难看。

### 第二步：全量备份，数据库单独导出

文件部分可以先跑一次 rsync 全量同步，数据库建议单独 dump：

bash
mysqldump -u root -p --single-transaction dbname > db_backup.sql
md5sum db_backup.sql


`--single-transaction` 让 InnoDB 在导出时不锁表，业务照常读写。直接拷贝数据库目录也可以，但前提是新旧两台机器的数据库大版本一致，跨版本复制目录，新机上的数据库多半起不来。

dump 完用 md5sum 生成校验值核对一遍，确认文件没损坏再往下走。

### 第三步：双阶段同步

- **第一阶段**：业务正常运行时，完整同步一次网站文件、静态资源和证书。这一步耗时最长，可能几十分钟到几小时，但用户完全无感知。
- **第二阶段**：低峰期停掉网站服务和定时任务（crontab 记得一起停），再跑一遍同样的 rsync 命令。增量同步只传变化的部分，通常几分钟就结束。

两阶段跑完，新旧机器的数据差异只剩停服之后新产生的部分，停机窗口自然就短了。把“迁移停机几小时”变成“停机几分钟”，靠的就是这一步。

### 第四步：切换上线

改 DNS 指向新 IP，在新机上重启 Nginx/Apache，把首页、登录、支付这些核心功能各走一遍。老服务器保留 3–7 天再释放，这期间解析还没生效的用户依然能落到老机上，算是一层兜底。

## 迁移完成后的验证清单

数据传完不等于迁移成功，三样东西必须查：

- **文件一致性**：对比关键目录的文件数量和大小，小文件用 `diff -r` 抽查内容；
- **功能可用性**：核心业务流程实际走一遍，数据库额外用 `EXPLAIN` 看看执行计划。有用户迁移时漏了索引，查询速度直接掉了 30%，这种问题不测根本发现不了；
- **性能基线**：`top` 看 CPU 和内存占用，`iostat` 看磁盘 IO，和迁移前的水平对比，差异明显就回头查配置。

## 常见问题

**VPS迁移要停机多久？**
取决于数据量和两机间带宽。可以粗算：1Gbps 端口跑满约 125 MB/s，100 GB 数据理论 15 分钟上下，1 TB 要两个多小时，实际速度通常还要打个对折。用双阶段 rsync 的话，真正停机的只有第二阶段增量同步那几分钟。

**换了新 IP 之后要做什么？**
改 DNS 解析（TTL 已经提前调低的话，半小时内基本生效），在新机上重新部署或续签 SSL 证书，然后盯着老机的访问日志看几天，确认流量切干净了再释放老机。

**迁移后网站打不开，先查什么？**
按顺序排查：防火墙和安全组放没放行 80/443 端口；Nginx/Apache 是否正常启动；数据库连接配置的地址和密码；DNS 是否已生效。SSH 登不上去就查 22 端口。
